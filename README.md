# TraceGuard

An ML model flags suspicious Bitcoin transactions, and a team of LLM agents investigates each flag and drafts a grounded report. A critic agent then checks every claim in the report against the collected evidence. The project uses real data from the Elliptic Bitcoin dataset.

Status: Phase 4a (LangGraph investigation agent built and demonstrated on 6 nodes)

## Results (Phase 2)

Splits are temporal and use labeled nodes only: fit = time steps 1-29, validation = 30-34, test = 35-49. Thresholds and calibration come from validation only. Illicit is the positive class. Test steps 43-49 follow a market shutdown ("post-shutdown"); steps 35-42 are "pre-shutdown". Full tables: [eval/results/phase2c.md](eval/results/phase2c.md), [eval/results/drift.md](eval/results/drift.md).

**Final model: LightGBM on the 165 original features, no structural features.** Reasons:

- Adding the structural graph features raised test PR-AUC by only 0.004 (0.7956 vs 0.7917), which is within noise.
- Pre-shutdown F1 was lower with them (0.885 vs 0.898).
- `wcc_size` is nearly a time-step proxy (every weakly connected component has at least 1,089 nodes, so each time step is essentially one component).

The structural model's numbers are kept in [eval/results/phase2b.md](eval/results/phase2b.md) as a negative-result ablation, and `src/ml/graph_features.py` is kept for the agent tools. Caveat: this decision cited test-set numbers, so the test period is no longer a pure holdout for the choice between these two models.

| Period | PR-AUC | Precision | Recall | F1 |
|---|---|---|---|---|
| Test overall (35-49) | 0.792 | 0.915 | 0.719 | 0.806 |
| Pre-shutdown (35-42) | 0.915 | 0.952 | 0.849 | 0.898 |
| Post-shutdown (43-49) | 0.039 | 0.083 | 0.018 | 0.029 |

(Validation-F1 threshold 0.788. Test prevalence is 6.5% overall, 9.2% pre and 2.5% post.) After the shutdown the model is close to useless: recall collapses at nearly every step from 43 on.

**Cost-based threshold.** The costs are assumptions, not measured: a false alert costs 1, a missed illicit node costs C in {5, 10, 20}, default C = 10. The default threshold chosen on validation is 0.2582 (raw score). On test it gives overall precision 0.654, recall 0.744, total cost 3,197 against 10,830 for flagging nothing. Post-shutdown it costs 1,846 against 1,690 for flagging nothing, so it does not pay for itself there.

**Calibration.** Isotonic regression on validation predictions. Test Brier 0.0263 raw and 0.0224 calibrated; test ECE 0.0289 raw and 0.0197 calibrated. Prevalence drops from 16.8% in validation to 6.5% on test, so calibration drifts and is worst post-shutdown.

**Drift monitor (label-free, [src/ml/drift.py](src/ml/drift.py)).** It does not cleanly separate pre- and post-shutdown steps. PSI is already "major" for many steps inside the reference period, the score PSI ranges overlap completely between pre and post steps, and the feature PSI flags essentially every step after the reference period (31-49), not just 43-49. It also flags steps where the model still works well. Details in [eval/results/drift.md](eval/results/drift.md).

## Agent tools (Phase 3a)

Plain Python functions in [src/tools/](src/tools/) with Pydantic inputs and outputs, registered in `TOOLS`: `score_transaction`, `get_neighbors`, `subgraph_summary`, `match_typology`, `check_model_health`. Rules: no tool returns a ground-truth label, tools never cross time steps, unknown ids return a structured error, and every output carries an `evidence_id`.

**Score scale.** Every score is the raw LightGBM `predict_proba` of the final model (trained with `scale_pos_weight`, so not a calibrated probability). The alert threshold 0.2582 (cost-based, C=10, an assumed cost) and the high-risk threshold 0.788 (validation-F1) were both chosen on this raw scale. A calibrated probability appears only as a separate, labelled field.

**Typology flags are structural resemblance only.** Elliptic has no typology labels. On labeled nodes in steps 1-34, the chain flag is informative (illicit rate 25.7% flagged vs 10.8% unflagged), while the fan-in and fan-out flags are anti-informative (1.9% and 0.0% vs about 12%). See [eval/results/typology_check.md](eval/results/typology_check.md).

**Model-health monitor (`check_model_health`).** It uses delayed labels: lag 2 steps, a 3-step window, reference recall from validation steps 30-34, degraded if window recall is below half the reference, at least 20 illicit nodes required. These constants were designed after the post-shutdown failure was observed, so the evaluation on steps 35-49 is not a blind test of them. Result: first flagged at step 47 (shutdown at 43), no false alarms in steps 35-42. See [eval/results/model_health.md](eval/results/model_health.md).

**Typology evidence direction.** `match_typology` now attaches, per matched pattern, the illicit rate among labeled nodes in steps 1-34 only, the baseline rate, the lift and an `evidence_direction` (`raises_risk`, `lowers_risk` or `uninformative`) from a rule fixed in advance: the 95% Wilson interval of the flagged rate lies entirely above, entirely below, or around the baseline. Current values: chain `raises_risk`, fan_in and fan_out `lowers_risk`. A `lowers_risk` pattern must never be described as suspicious.

## Regulation retrieval (Phase 3b and 3c)

Four documents are indexed from `data/raw/regulations/` (gitignored): the FinCEN 2019 CVC advisory, the FinCEN 2003 SAR narrative guidance, the FATF 2020 virtual-assets red-flag report and the FIU-IND 2026 virtual digital assets guidelines ([src/rag/SOURCES.md](src/rag/SOURCES.md), [src/rag/manifest.yaml](src/rag/manifest.yaml)). The India document is a scan and was read with local OCR (rapidocr); checked against page images, the body text is accurate with minor errors listed in SOURCES.md. Chunks are about 250 tokens with about 15% overlap and an evidence id like `reg:<doc_id>:p<page>:c<n>` (physical PDF page). Retrieval is BM25 plus dense vectors (BAAI/bge-small-en-v1.5 in FAISS) fused with reciprocal rank fusion. A cross-encoder reranker (ms-marco-MiniLM-L-6-v2 over the top 20) is available as an option (`rerank=True`) but is **not the default**: under a rule fixed in advance it had to raise hit@1 by at least 0.10, and it raised it by 0.045, at about 2.5 s per query on CPU. Tools: `search_regulations`, `get_regulation_chunk`. Evaluation on a 28-question golden set (22 scored): [eval/results/retrieval.md](eval/results/retrieval.md); failure diagnosis: [eval/results/error_analysis.md](eval/results/error_analysis.md). Retrieval is weak on this set (hybrid hit@3 about 0.59) and weakest on the India questions, so retrieved text is a lead for an analyst, not proof. The set is small, so differences between modes are noisy.

`match_typology` returns `retrieval_query: null` and a note for any pattern whose evidence direction is `lowers_risk`, so an agent cannot fetch red-flag text for it.

**Final retrieval configuration (Phase 3d, frozen; [eval/results/retrieval_final.md](eval/results/retrieval_final.md)).** Hybrid retrieval with contextual chunk headers (`<publisher> <year> - <title> - <section heading>` added to the text used for BM25 and embeddings only); no reranker; no LLM query rewriting. The choices came from keep rules fixed before the experiments, on the 19 document-grounded golden questions. Headers passed their rule (hit@3 +0.053 against a +0.05 threshold, hit@1 unchanged); Gemini query rewriting (`gemini-3.5-flash-lite`, temperature 0, cached in `eval/results/rewrites.json`) missed its rule (hit@3 +0.053 against +0.10), so `search_regulations` only rewrites when asked (`rewrite=True`). Both margins are a single question, so treat them as weak evidence. Search results carry a `quotable` flag; it is `false` for the India document, which comes from OCR and must not be quoted directly. Golden-set changes are logged in [eval/GOLDEN_CHANGELOG.md](eval/GOLDEN_CHANGELOG.md).

## Investigation agent (Phase 4a)

`python -m src.agents.run <tx_id>` runs a LangGraph agent (`src/agents/graph.py`, Gemini `gemini-3.5-flash-lite` at temperature 0, name set in `src/agents/config.py`). We do **not** claim it improves detection; the claim is grounded, explainable investigations with honest limits. Triage is deterministic: if the model-health check says the model has degraded at that time step the run ends as `cannot_assess` (no risk rating is given), and a low-band node with no risk-raising pattern ends as `no_action_model_based` without any LLM call. Otherwise an investigator LLM calls the graph tools (at most 8 calls), a regulation step searches only for patterns with a retrieval query (at most 3 searches), a writer fills a structured memo of claims that each cite evidence ids from the run's evidence ledger, and a critic checks them: deterministic checks (citations exist, every number appears in the cited output, a `lowers_risk` pattern is never called suspicious, quotes are verbatim and from `quotable` chunks only, SHAP features stay anonymous) and then an LLM check of whether the cited evidence supports each claim. A failed draft is rewritten at most twice; after that the failing claims are removed and the memo is marked "partially verified". Caps (tool calls, searches, critic loops, LLM calls) end a run with `budget_exceeded` and a partial memo, never a crash. Every run is logged to `eval/traces/<tx_id>.json`. Demo on 6 nodes chosen by fixed rules, with the memos, the critic's verdicts and the odd behaviour left in: v1 in [eval/results/agent_demo_v1.md](eval/results/agent_demo_v1.md) and v2 (after the fixes below) in [eval/results/agent_demo_v2.md](eval/results/agent_demo_v2.md). Tests use a scripted fake LLM and never touch the network.

**Phase 4b changes.** A deterministic `signal_conflict` sentence is computed in triage when the model score and another signal (a risk-raising pattern for a low band, only risk-lowering patterns for a high band, or the in-neighbours' alerts) point in different directions; the writer must copy it unchanged and the critic checks it. Memos at time step 43 or later get a dataset-specific note (based on hindsight from the published test results) in their limitations, and every memo states that the health monitor lags and first flags the collapse at step 47. Regulation text is shown as "Regulatory background (context, not evidence about this transaction)", and the SHAP features are merged into one claim. None of this changes the gating.

**One example of the critic catching an ungrounded claim (one example, not a rate).** In the v1 demo run for transaction 97870846, round 1, the writer produced the claim "Model health check status was ok with a window recall of 0.880435 and reference recall of 0.98308 across 3 window steps." The deterministic check rejected it with "numbers not found in the cited evidence: 3": the number 3 is not a value in the cited health evidence (it was counted from the window by the writer). The rewrite in round 2 dropped the number and passed. (Source: `eval/traces/v1/97870846.json`.)

## Phase 5a: agent evaluation

**Step 0 (schema fix).** Claims no longer have a `quote` field; only regulatory background may carry a quote, and only for quotable chunks (the critic also rejects an activity claim that contains a quotation). This removes the Phase 4b run-4 failure where the writer put score text in the `quote` field. The only prompt edit was the sentence describing the claim shape.

**Pre-registered evaluation.** [eval/agent_eval_spec.md](eval/agent_eval_spec.md) (commit `9771079`) fixed the 40 cases (seed 42, 7 strata), the three arms (A0 ML only, A1 the writer's first draft, A2 the full system with the critic) and all metrics before any case was selected or run. Results: [eval/results/agent_eval/report.md](eval/results/agent_eval/report.md); bugs found during the evaluation, with case ids and before/after numbers: [eval/results/agent_eval/BUGLOG.md](eval/results/agent_eval/BUGLOG.md). All 40 cases ran. Headline, stated plainly: groundedness is 100% in all three arms once the metric bugs were fixed (so it does not separate the arms), completeness is 79% for A0 and 96% for A1 and A2, there were no policy violations in any arm, and the critic changed the memo in 6 of the 27 runs that reached it (quote and reviewer rejections). Typology evidence with its direction appears in only 65% of the memos where a pattern matched (11 of 17), in both A1 and A2. Four bugs were found and fixed during the evaluation, one of them in the system itself (the critic read a score such as 4.5e-05 as two numbers and wrongly rejected it); the two affected cases were re-run. Nothing here measures whether the agents improve detection.

## Phase 5b: judge, fault injection, hand-check results

Pre-registered in [eval/agent_eval_5b_spec.md](eval/agent_eval_5b_spec.md) (commit `493c674`), measurement only (no system code, prompt or threshold changed). Report: [eval/results/agent_eval/report_5b.md](eval/results/agent_eval/report_5b.md). The Phase 5a metric formerly called "groundedness" is now called "citation and number consistency" because it shows a ceiling effect (100% in every arm) and shares a blind spot with the critic. All runs are complete (a daily free-tier quota interrupted them once; see [BUGLOG_5b.md](eval/results/agent_eval/BUGLOG_5b.md)): all 171 unique claims were judged (142 by `gemini-3.5-flash-lite`, the writer's own model, so the judge is not independent of the writer for most claims; 29 by `gemini-3.8-flash`), and the critic was tested on 140 injected faults (98 applicable, all caught; 0 of 20 untampered controls rejected).

**Hand-check result, in one paragraph.** A human checked 110 claims in 15 runs and flagged 7 (5 unsupported, 2 overstated). The critic rejected 11 claims, the human agrees with 4, and the critic missed 3 of the 7. The judge caught 2 of the 7 (1 could not be judged) and had 1 false positive. The deterministic citation and number consistency metric caught 1 of the 7 (1 could not be evaluated) and had 1 false positive, so the 100% ceiling hides most real errors. These natural errors are mostly subtle (a claim that drops a hop qualifier, covers more than the cited evidence, or generalises a case study), unlike the synthetic faults, which were all caught. Caveats: one human, 15 runs of which 6 were chosen because the critic changed them, only 7 flagged claims (so every rate has a wide interval), and the human saw before scoring which run's claim had been flagged (tx 73002915), so that run was not blinded.


## Phase 5c: facts rendered by code (agent-v3, fixed in agent-v3.1)

Motivation: the Phase 5b hand check found 7 errors in 110 claims, all of them an LLM paraphrase of a tool fact. Pre-registered in [eval/agent_eval_5c_spec.md](eval/agent_eval_5c_spec.md) (commit `b19fb18`, amended before any run in `589b497`; the previous design is tagged `agent-v2`). Design v3 (`config.DESIGN = "v3"`, default; `"v2"` keeps the old behaviour): neighbour, subgraph, typology, score, SHAP-feature and health claims and the regulatory background are rendered by code from the tool outputs (`src/agents/facts.py`); regulation text is a verbatim excerpt of at most 40 words, or only a label for non-quotable documents; the writer LLM only writes an executive summary of at most 3 sentences and a list of next checks, and the critic verifies the summary and recomputes the code-built parts. The spec also answers why `get_neighbors` (directed chains, focal node excluded) and `subgraph_summary` (undirected radius, focal node included) report different counts for the same node. Full report: [eval/results/agent_eval_5c/report_5c.md](eval/results/agent_eval_5c/report_5c.md). 30 fresh nodes (seed 43, disjoint from earlier sets), v2 (tag `agent-v2`) versus v3 (tag `agent-v3`), same model and frozen retrieval.

**1. The pre-registered rule was not met.** The rule was: adopt v3 if mean completeness improves by at least 0.05 and there are no new policy violations. The gain was +0.031 (97% to 100%; bootstrap interval [0.01, 0.06]) against the 0.05 threshold, so the rule outcome is "do not adopt v3 on this rule". Why it fell short: both designs have no policy violations and 9 of the 30 nodes take the deterministic path where they are identical by construction, so only 21 nodes can differ. A pre-registered amendment also states that completeness is near-tautological for v3 (code inserts the required items): it measures a design guarantee, not LLM quality, and the keep rule was applied as written. Citation and number consistency is 100% in both designs (128/128 and 235/235), so it does not separate them.

**2. The omission finding replicated on fresh nodes.** In v2, typology evidence with its direction appears in only 5 of 8 memos where a pattern matched (62%), and a neighbour summary in 17 of 21 (81%); in v3 both are 100% because code writes them. This is the 5a finding (65%) on new nodes.

**3. What v3 changed.** 174 of 235 memo statements are rendered by code (v2: 28 of 128). Prompt tokens 179k versus 215k (-17%), output tokens 20.7k versus 22.8k, mean wall time without throttle waits 7.3 s versus 12.6 s. LLM calls were slightly higher (143 versus 131 in total) because of extra rewrite rounds (see 4).

**4. The critic rejected more in v3, and why.** 8 of 21 writer runs had a rejected item in v3, 4 of 21 in v2; two v3 runs ended partially_verified against one for v2. A post-hoc diagnosis of all 31 rejected items ([rejection_diagnosis.md](eval/results/agent_eval_5c/rejection_diagnosis.md)) classified v2's as 8 genuine LLM errors, 1 check too strict, 1 possible check bug, and v3's as 2 genuine, 14 too strict, 5 possible check bugs. Nine of v3's ten deterministic rejections came from the new next-check rule, which rejected any digit, including "hop 1" and feature ids like f53; most of the rest were the LLM reviewer objecting to correct sentences that restate code-built wording ("undirected subgraph", "delayed-label window"), or contradicting its own reason.

**5. The bugfix (agent-v3.1).** Only the next-check rule was changed: feature ids, hop references and time step references are now allowed, any other number is still rejected (tests cover `hop 1`, `f53, f59, f163`, and still reject `score 0.9`, `5 neighbours`, `0.25`). Verification, not an evaluation: the 8 nodes whose v3 runs had rejections were re-run with agent-v3.1 ([bugfix_report.md](eval/results/agent_eval_5c_bugfix/bugfix_report.md)). Rejected items fell from 21 to 10 (genuine 2 to 2, too strict 14 to 8, possible check bug 5 to 0), next-check rejections from 9 to 2 (both correct: they contained 0.783844 and 5598), and statuses went from 6 verified and 2 partially_verified to 7 and 1. These nodes were used for the diagnosis, so nothing is claimed about generalisation, and the headline 5c numbers remain the agent-v3 run. The reviewer was not changed and is still too strict; no further agent changes will be made (freeze): Phase 6 builds on `agent-v3.1`.

**6. Hand-check (one human, blinded to who wrote each statement).** Code-built claims: 0 of 20 wrong (95% Wilson interval [0%, 16.1%]). LLM-authored summary sentences: 1 of 61 overstated (1.6%, interval [0.3%, 8.7%]): item H042, which attributes a signal conflict to the mixed directions of feature contributions, which the evidence does not support (it only supports a conflict between the low score and the chain pattern). The deterministic consistency metric also called that sentence grounded. These rates are not comparable to the Phase 5b development-set rate (3 of 79). No claim is made that v3 is more accurate than v2; only that two error classes (neighbour and subgraph counts merged or missing hop and direction, and LLM paraphrase of regulation text) cannot occur in v3 by construction. The sheet and key are `handcheck_5c.csv` and `handcheck_5c_key.json` in `eval/results/agent_eval_5c/`.

**Limitations.** The classification of rejections is one reader's judgement. n = 30 nodes (21 that can differ), so intervals are wide. The bugfix verification uses nodes that informed the diagnosis (development-contaminated) with one run each, and the LLM is not deterministic. The hand-check has one human, 20 code-built claims and 61 summary sentences. One LLM is investigator, writer and reviewer. Nothing in Phase 5c measures whether the agents improve detection.
